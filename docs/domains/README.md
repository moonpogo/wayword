# WAYWORD - Codex Domain Operating System

## v1 Foundational Studio Structure

### Purpose

Wayword is transitioning from:
- a single writing interface

into:
- a longitudinal perceptual observatory

The purpose of this system is to:
- prevent conceptual collapse
- preserve doctrine integrity
- isolate responsibilities
- reduce AI-assisted codebase drift
- create bounded operational reasoning
- scale product depth without becoming dashboard sludge

These are NOT "AI employees."
These are:
- operational lanes
- bounded reasoning contexts
- domain ownership systems

The founder remains the final integrator.

### Root Principle

Each lane:
- protects a specific class of truth
- has bounded authority
- operates under explicit doctrine
- may NOT freely redesign adjacent systems

Good Wayword development emerges from:
- constrained competing forces

NOT:
- omniscient generalized AI behavior

### Recommended Domain Structure

1. Architecture
2. Observatory
3. Safety & Privacy
4. Editorial Doctrine
5. QA Regression
6. Research
7. Brand & Marketing
8. Conductor (Pruner / Systems Steward)

### Canonical Workflow Protocol

Domain-lane work must follow the canonical operating protocol in [`WORKFLOW_PROTOCOL.md`](./WORKFLOW_PROTOCOL.md).

This protocol is the required path for moving work from founder intent to doctrine to prototype to QA hardening to founder go/no-go decision.

Unattended multi-lane continuation must follow [`NIGHT_SHIFT_PROTOCOL.md`](./NIGHT_SHIFT_PROTOCOL.md), which is the canonical protocol for bounded overnight work.

Major initiative execution memory lives in [`/docs/initiatives/`](/Users/andrewrodriguez/Desktop/wayword/docs/initiatives/), with one folder per initiative.

Conductor governance and anti-entropy authority is defined in [`conductor.md`](./conductor.md). The Conductor reduces entropy and process bloat; it does not create new product work.

Initiative recursive continuation state rules are defined in [`INITIATIVE_RUNTIME.md`](./INITIATIVE_RUNTIME.md). This runtime enables bounded recursive continuation only under founder-approved scope.

### Branch Discipline

Each lane works in isolated branches.

Examples:
- `architecture/persistence-refactor`
- `observatory/trace-field-v0`
- `safety/inference-ceilings`
- `editorial/mirror-copy-pass`
- `qa/season-wheel-regression`
- `research/climatology-reference-study`
- `brand/summer-observatory-campaign`

### Workflow

1. Founder defines product intent.
2. Relevant lane receives scoped task.
3. Lane operates within bounded authority.
4. QA validates.
5. Safety validates.
6. Founder integrates final decision.

### Founder Role

The founder is:
- final integrator
- doctrine arbiter
- systems synthesizer

The founder resolves:
- safety vs observatory tension
- marketing vs doctrine tension
- architecture vs velocity tension
- aesthetics vs usability tension

The founder is NOT:
- a generalized lane
- passive approver
- automation overseer

The founder shapes:
- overall coherence
- philosophical integrity
- strategic direction

- bounded expertise
